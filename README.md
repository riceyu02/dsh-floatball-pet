# DSH 悬浮球桌宠（dsh-desktop-pet）

> 由 [Riceyu02](https://github.com/Riceyu02) 维护的第三方社区插件。本项目与 DeepSeek AI
> 无隶属、认可或合作关系。

一个常驻桌面的**系统级悬浮球**：平时就是一颗小鲸鱼球，鼠标移上去**向右展开成灵动岛**——
上方显示 DeepSeek 余额、下方显示 DSH 运行时长（精确到秒）、最右侧一个设置按钮；点设置按钮，
**上方升起设置面板**，拖滑块就能同时改变悬浮球和灵动岛的大小。**单击悬浮球即可唤起
DeepSeek Harness 窗口**。

它现在同时提供两种运行方式：

- **DSH 插件（推荐）**：安装进 desktop profile，由 DSH 启动和回收；退出 DSH 后悬浮球自动退出。
- **独立 Electron 程序**：保留原来的启动器；DSH 关掉或最小化到托盘，悬浮球仍可独立运行。

## 功能

| 能力 | 说明 |
|---|---|
| **悬浮球** | 无边框、透明、置顶、不占任务栏；可任意拖动，位置自动记忆；图案取自你提供的立绘 |
| **灵动岛** | 鼠标移入球体 → 向右展开（贴近屏幕右侧时自动改为**向左展开**） |

| **展开动画** | 设置里的开关：展开时岛内背景有水下的动静 —— 气泡上浮、一道微光扫过、偶尔游过一只小鲸鱼 |

| **长度贴合** | 灵动岛宽度按内容实测，齿轮紧跟在文字后面，不留空白 |
| **余额** | 上方一行，实时读取 DeepSeek 账户余额；变化时数字有一次高亮闪烁 |
| **运行时间** | 下方一行，**精确到秒**（`21时 37分 10秒`），每秒自增；DSH 未运行时显示「未运行」 |
| **设置按钮** | 灵动岛内侧紧贴文字的一个齿轮；点击后设置面板从**上方**弹出（贴近屏幕顶部时改为下方） |
| **大小滑块** | 拖动即改悬浮球直径（40–96 px），**灵动岛、字号、齿轮同步等比缩放**，逐帧平滑过渡并持久化 |
| **唤起 DSH** | 单击悬浮球：DSH 已在运行则把它的窗口拉到最前（最小化也会还原）；未运行则启动 |
| **拖动** | 按住球体拖动；位移超过 4 px 判定为拖动，不会误触发「唤起 DSH」 |
| **托盘** | 托盘菜单可显示悬浮球、打开 DSH、快速切换大小、退出 |
| **开机自启** | 设置面板内的开关（写入当前用户登录项） |

## 运行

### 作为 DSH 插件安装（推荐）

插件采用 Cordis bundle 结构，主插件只负责生命周期，透明置顶窗口仍放在独立 Electron helper
里。这样不会和 DSH 主窗口争 Electron 单实例锁，悬浮球崩溃也不会带倒 DSH。

先生成自带 Windows x64 Electron 运行时的离线安装包：

```powershell
cd D:\deepseek_project\plugin-project\dsh-desktop-pet
npm run build:dsh-plugin
```

产物位于 `artifacts\dsh-desktop-pet-0.2.0.tgz`。安装到桌面版实际使用的 `desktop` profile：

```powershell
& 'D:\DeepSeekHarness\resources\runtime\cli\bin\dsh.cmd' `
  plugin --profile desktop add `
  'D:\deepseek_project\plugin-project\dsh-desktop-pet\artifacts\dsh-desktop-pet-0.2.0.tgz'
```

完全退出并重新打开 DSH 后生效。插件模式有这些行为差异：

- DSH 启动时自动启动悬浮球；插件卸载、禁用或 DSH 退出时自动关闭，不留孤儿进程。
- 偏好和日志写入 `<DSH profile>\data\dsh-desktop-pet\`，不会与独立版混用。
- 设置面板不再显示“开机自动启动”；开机启动由 DSH 自己负责。
- “本次关闭”只关闭到下一次 DSH 启动，不会修改或卸载插件。
- 标准 Chromium 沙箱若在 5 秒内异常退出，宿主只用 `--no-sandbox` 兼容模式重试一次。

> 安装包内含完整 Electron 运行时，因此体积较大，但安装和首次启动都不需要再联网下载运行时。

### 作为独立程序运行

#### 前置

- Windows 10/11
- Node.js（首次安装 Electron 与启动应用都要用）
- 已安装 DeepSeek Harness（安装位置会自动查找，见下；也可以用 `DSH_DESKTOP_EXE` 指定）

> **DSH 在哪是怎么找的。** 只有**DSH 没在运行时**才需要猜路径：已经在跑的时候，
> 真实路径是从活动进程里读回来的，所以那种情况在任何机器上都本来就对。
> 冷启动时按顺序找这几处（`<名字>` 两种拼写都会试：`DeepSeek Harness` 和 `DeepSeekHarness`
> —— 安装程序和文档对它是否带空格的说法不一致）：
>
> | 顺序 | 位置 |
> |---|---|
> | 1 | `%DSH_DESKTOP_EXE%`（显式指定，最高优先级） |
> | 2 | `%LOCALAPPDATA%\Programs\<名字>\DeepSeek Harness.exe`（安装程序默认装这里） |
> | 3 | `%ProgramFiles%\<名字>\DeepSeek Harness.exe` |
> | 4 | `%ProgramFiles(x86)%\<名字>\DeepSeek Harness.exe` |
> | 5 | `%USERPROFILE%\<名字>\DeepSeek Harness.exe`（便携版解压到用户目录旁） |

#### 首次安装

```powershell
cd dsh-desktop-pet
npm install
```

> Electron 二进制走 GitHub 下载，慢或失败时先设镜像：
> ```powershell
> $env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"
> npm install
> ```
> npm 11 若提示 `install-scripts ... not yet covered by allowScripts`，说明 postinstall 被策略拦下，补一条：
> ```powershell
> node node_modules/electron/install.js
> ```

#### 启动

双击 **`启动悬浮球.cmd`**（也可以 `npm start`）。它会：

1. 先起 `tools/focus-agent.cjs`（见下「为什么要有个帮手」）；
2. 用**标准模式**启动 Electron（不加 `--no-sandbox`，进程权限完整）；
3. 4 秒后如果进程已经没了，说明 Chromium 沙箱在本机起不来，**自动改用 `--no-sandbox` 重试**。

两种模式的启动结果都会打印在窗口里，日志写在 `%APPDATA%\DSH 悬浮球\pet-console.log`。

#### 该点哪一个（打包版）

打包版**没有启动器**，所以两个模式各给一个快捷方式，选哪个由你决定，而不是它偷偷猜：

| 入口 | 沙箱 | 什么时候用 |
|---|---|---|
| **启动（标准模式）** | 开 | **默认点这个。** 沙箱正常的机器上它权限完整，连焦点帮手都不太需要 |
| **启动（兼容模式）** | 关（`--no-sandbox`） | 标准模式双击后**毫无反应**时才用 —— 那是沙箱初始化失败的特征 |

判断依据：**安装路径里含中文等非 ASCII 字符时，Chromium 沙箱一定起不来**（见下文「两个和主题无关的坑」）。
失败是**静默**的（进程一闪就没、日志一个字节都没写），所以只能靠"点哪个"来区分，
而不是让它自动降级 —— 正常机器上偷偷带 `--no-sandbox` 是白降安全性。

开发版（`启动悬浮球.cmd`）仍然是**自动**的：先试标准模式，4 秒后进程没了就自己换兼容模式。
想分别试的时候，另有两个严格入口 `启动（标准模式）.cmd` / `启动（兼容模式）.cmd`，
它们分别传 `--strict-sandbox` / `--force-no-sandbox` 给 `tools/launch.cjs`，不会回退。

#### 退出

设置面板 → **退出**；或托盘图标右键 → 退出。

## 数据从哪来

### 余额

按优先级依次尝试，任何一步失败都自动降级，不会显示成 0。

1. **DSH 账号登录态（推荐，零配置）** —— 读 `$DSH_HOME/.credentials.yaml` 里
   `deepseek-account-platform/default` 的授权 token，请求
   `GET https://platform.deepseek.com/api/v0/users/get_user_summary`。
   请求头与 DSH 自己一致（`x-dsh-auth-token` + 五个 `x-client-*`）。
   以 `normal_wallets` 同币种之和为余额，`bonus_wallets` 为赠金（悬浮提示里单列）。
2. **`DEEPSEEK_API_KEY`** —— 凭据文件或环境变量里有平台 key 时，改用
   `GET https://api.deepseek.com/user/balance`。
3. **离线兜底** —— 都拿不到时退回鲸鱼挂件账本 `$DSH_HOME/.dshw-usage.json` 的 `lastBalance`，
   并在提示里标注「上次观测值（离线）」。

刷新：启动一次、每 5 分钟一次；悬停不会额外请求。鼠标停在余额上可看到**来源**与失败原因。
余额只读、只发往上面写死的官方域名，**不会修改或清除 DSH 的任何凭据**。

### 运行时间

1. **存活判定**：TCP 连 DSH 的 Web 端口（取 `$DSH_WEB_URL`，否则读
   `$DSH_HOME/dsh-web-url.log`，默认 `19387`）——纯 Node，不起子进程。
2. **起始时刻**：确认存活后，用 PowerShell 取 `DeepSeek Harness` 进程（或占用该端口的进程）
   里最早的一个 `StartTime`；取不到时退化为自己第一次看到它存活的时刻。

刷新：每 15 秒一次；界面每秒重绘，所以秒数是实时跳的。

## 实现要点

几个不那么显然、但决定了这个桌宠能不能好好工作的细节。

- **整块窗口是透明的，命中测试在主进程做。**
  Electron 的 `setIgnoreMouseEvents(true, { forward: true })` 并不保证把 `mousemove`
  转发进渲染进程，所以改成主进程每 40 ms 轮询真实光标位置，自己算球体方块、胶囊矩形、面板矩形，
  据此同时决定「是否穿透」和「灵动岛是否展开」，再把状态推给渲染进程。
  球体按**外接方块**判定、胶囊与面板各外扩 8 px，所以「停在球上或岛上」不会因为差几个像素就收起。
- **尺寸动画由主进程逐帧推进。**
  只在 CSS 里过渡 `--s` 是不行的：窗口会被立刻改小，而球还停在旧尺寸 —— 结果是球被裁掉一截。
  所以主进程每 8 ms 让 `renderedSize` 朝目标缓动一次，同一帧里既改窗口边界又下发 CSS 变量，
  两者永远一致。拖动滑块时渲染进程会给 `#stage` 加 `.resizing` 关掉那条展开/收起的宽度过渡，
  避免和逐帧推进打架。
- **灵动岛宽度按内容实测。**
  `.island-inner` 用 `width: max-content`，即使收起时也能量出真实宽度；量到的值写进 `--island-w`
  并报给主进程（窗口宽度和悬停区域都用它）。
- **贴近边缘自动翻转。** 球心过屏幕中线后，胶囊改 `row-reverse`，灵动岛改为向左展开，
  齿轮自动落到外侧那一端。
- **透明窗口里不要有整窗合成层。**
  原先 `#stage` 上挂了 `opacity`，Chromium 会为此把整窗提升成一个图层，透明窗口上就多出一层
  淡淡的矩形底 —— 看起来正是「悬浮球周围有一圈黑色方框」。现在不透明度由 `.capsule` / `.panel`
  各自承担，整窗保持完全透明。
- **PowerShell 用 `-EncodedCommand` 调用。**
  多行脚本、here-string C# 和中文路径混在一起时，`-Command` 的引号转义极易碎掉；
  base64(UTF-16LE) 没有这个问题。脚本里再把 `[Console]::OutputEncoding` 设成 UTF-8，中文报错才不是乱码。

### 为什么要有个「焦点帮手」

这是最花时间的一个坑，值得单独说明。

Windows 的 `SetForegroundWindow` 只允许**前台进程**调用，而后台进程要用 `AttachThreadInput`
才能抢到前台——这段逻辑要用 `Add-Type` 现场编译 C#。问题在于：

- Chromium 沙箱在部分机器上**起不来**（本机上就是），只能退到 `--no-sandbox`；
- 而 `--no-sandbox` 会让进程拿到一个**受限令牌**：既枚举不到其它进程，也编译不了那段 C#
  （`A required privilege is not held by the client`），WMI 和 explorer 这两条逃逸路线同样被拒（`拒绝访问`）。

于是启动器**在 Electron 之前**先起一个 `tools/focus-agent.cjs`（普通 Node 进程，继承启动器的完整令牌），
它监听 127.0.0.1 上的随机端口，把端口与一次性 token 写进
`%APPDATA%\DSH 悬浮球\focus-agent.json`。悬浮球点击时按顺序尝试：

**这个帮手有两个启动者，都是有意的**：开发版由 `tools/launch.cjs` 在 Electron 之前启动（令牌最好）；
打包版没有启动器，所以**悬浮球自己在 `whenReady` 里把它拉起来**（用 `DSH悬浮球.exe` +
`ELECTRON_RUN_AS_NODE=1` 当 Node 用，对方机器上不需要装 Node）—— 漏掉这一条正是打包版
"点悬浮球没反应"的根因，详见下文踩过的坑。

1. **自己来** —— 令牌完整时直接成功（正常机器就是这样）；
2. **找帮手** —— 带上 token 请求 `POST /focus`，由帮手调用同一段「抢前台」逻辑；
3. **走 WMI** —— 让 WMI 服务创建一个进程来执行（部分机器上此路可通）。

三条都失败时**只报告失败，绝不会再启动一份 DSH**（见下）。另外，点击后如果 DSH 没能拿到
前台，悬浮球会主动 `blur()` 把自己让开，并在灵动岛里用运行时间那一行短暂提示「DSH 未响应前置」。

#### 这一块踩过的四个坑（都已修）

- **「隐藏」和「最小化」是两回事，而且隐藏的那个会假装成功。** 把 DSH 的窗口关到后台
  （`ShowWindow(SW_HIDE)`，也就是点 X 收进托盘的效果）之后：
  - `WINDOWPLACEMENT.showCmd` **仍然是 `SW_SHOWNORMAL`** —— `SW_HIDE` 根本不会更新它，
    所以「按 showCmd 判断是否隐藏」是错的，只能看 `IsWindowVisible`；
  - 更阴的是 **隐藏的窗口仍然会被 `GetForegroundWindow()` 返回**。于是原来那句
    `return GetForegroundWindow() == h;` **报告成功，窗口却纹丝不动** ——
    表现就是「关掉之后点悬浮球再也打不开」。
    现在先 `SW_SHOW` 再前置，并且校验条件改成
    `GetForegroundWindow() == h && IsWindowVisible(h)`（对已可见的窗口调 `SW_SHOW` 是无害的，
    所以这个判断两个方向都安全）。
- **最小化的窗口会被尺寸过滤掉。** 找窗口时按「宽 ≥ 400、高 ≥ 300」排除消息窗、GDI+ 窗，
  但 Windows 给**最小化**窗口的矩形是哨兵值 `-32000` 附近，算出来只有一百多像素宽，
  于是 DSH 一旦被最小化就**永远找不到**。现在改用 `GetWindowPlacement` 的 `normalPosition`
  （还原后的矩形）判断尺寸。
- **不要用 `SwitchToThisWindow`。** 这个老 API 是**切换**语义：窗口已经在前台时会把它**最小化**。
  现在整条链路只做加法（show / restore / focus）。
- **DSH 已经在跑、而且有窗口时，绝不能再次启动。** 第二次启动会被运行中的实例当作
  `second-instance` 接走，而 DSH 对它的处理并不会把窗口提到前面。
  **例外**：如果 DSH 在跑但**一个窗口都不剩**（窗口被销毁、只剩进程），那就只能重新启动它 ——
  所以前置失败会带上原因（`no-window` / `blocked` / `error`），只有 `no-window` 才走重启动。
  另一条独立的进程（`tools/focus-agent.cjs`）也要把原因一起回传，主进程才能区分这两种情况。
- **打包版里压根没人启动焦点帮手，所以点悬浮球什么都不会发生。**（这条拖到最后才被发现）
  帮手原来是**只由 `tools/launch.cjs` 启动**的 —— 而打包版没有启动器，于是：
  帮手从来没被启动过 ⟹ `focus-agent.json` 从来没被写过 ⟹ 点击时找不到端口 ⟹
  只能靠悬浮球自己去抢前台，而它带着 `--no-sandbox` 的受限令牌**必然失败** ⟹
  表现就是**点了没反应**（而且日志里一切正常，因为没有东西报错）。

  现在**应用启动时就自己把帮手拉起来**（`dsh.startFocusAgent`）。两个细节让它能在打包版里成立：

  - **用 `process.execPath` + `ELECTRON_RUN_AS_NODE=1`。** 对方机器上不一定装了 Node，
    而 Electron 自己的 exe 是这台机器上**唯一保证存在的 Node 运行时**。
    不加那个变量它会当成"再启动一份悬浮球"。
  - **顺手带 `--no-sandbox`。** 理由和悬浮球本身一样：沙箱起不来的机器上，
    子进程会在任何 JS 跑起来之前就死掉。

  启动时机放在 `whenReady` 里（而不是等第一次点击），这样点击时帮手**已经在监听**，
  不需要等一个进程启动；`tools/launch.cjs` 那条路**保留**，因为它能更早启动、
  拿到的是启动器的完整令牌。两条路都先读握手文件再探测 `/health`，所以不会启重。
- **`Add-Type` 在受限的进程树里根本编译不了 C#，这才是「点了没反应」的最终原因。**
  `Add-Type` 编译时会临时起一个 `csc.exe`，而**创建子进程这件事**在某些进程树里会被拒绝：

  ```
  Add-Type : ok（正常启动的进程）
  Add-Type : Access is denied（应用那套进程树）—— System.ComponentModel.Win32Exception
  ```

  实测对照（同一台机器、同一段脚本，唯一变量是"从哪套进程树出去"）：

  | 上下文 | `Add-Type` | 枚举 DSH 窗口 |
  |---|---|---|
  | 桌面正常启动的进程 | ok | 看得见（`VIS ... — DeepSeek Harness`） |
  | 任务计划程序创建的进程 | ok | 看得见 |
  | 悬浮球那套进程树（含它起的助手） | **Access is denied** | **看不见** |

  于是 `focusDshStrong` 抛错、窗口也找不到，四条聚焦路线全灭 ✗ 而悬浮球只会把它
  报成 `error`，看着像"窗口问题"，其实和窗口无关。

  **修法：把那段 C# 预编译成 DLL 随包发走，运行时按字节交给 CLR**（`[Reflection.Assembly]::Load`）。
  这条路线**不需要编译器**，也不需要 `Add-Type -Path` 那道"程序集来自不受信任位置"的检查
  （实测 `Add-Type -Path` 会撞 `HRESULT 0x80131515`）。在**同一个受限上下文**里实测：

  ```
  focusDshViaDll -> true | reason: already
  focusDsh       -> true | reason: already      ← 整条链被这一条救活
  ```

  DLL 由 `tools/build-focus-dll.cjs` 在打包时生成（`assemble.cjs` 会自动调用），
  放在 `resources/app/src/PetFocus.dll` —— **和应用代码同一个文件夹**，因为
  `__dirname` 在打包 app 和手工组装的目录里不一样，往外爬一层只在其中一种布局里成立。
  另外助手 `/health` 会回报 `capable` 字段，能力不足时悬浮球**跳过**它，不再产生误导性的 `error`。

> 两个和主题无关、但同样致命的坑：
>
> 1. **安装路径含非 ASCII 字符时 Chromium 沙箱一定起不来。** 项目原先放在
>    `D:\deepseek_project\插件制作\` 下，把同一份代码复制到纯英文路径后标准模式就能启动，
>    所以现在已经挪到 `D:\deepseek_project\plugin-project\`。**建议保持纯英文路径。**
> 2. 即便路径是英文，**从某些受限的父进程（沙箱宿主、被降权的令牌）里拉起 Electron，
>    标准模式仍会稳定失败**：进程一闪就没、日志一个字节都不写，退出码 `0x80000003`
>    （`STATUS_BREAKPOINT`）。本项目的开发环境正是如此。这不是程序的问题 ——
>    从资源管理器双击启动不会遇到；而且兼容模式 + 焦点帮手照样能用。

### 拖动大小为什么不卡

滑块拖动时 `input` 事件是按鼠标移动频率来的，一秒上百次。最初的实现里，每个事件都会：

1. `store.save()` —— **同步**写偏好文件（`writeFileSync` + `renameSync`）；
2. `push()` —— 推一份包含余额、进程探测结果的完整快照；
3. 渲染进程每帧再回一次 `pet:metrics`，主进程收到就 `applyLayout()`。

三件事都在拖动的关键路径上，卡顿就是这么来的。现在：

- 偏好写文件改成**防抖 400 ms**，退出时再立即落盘；
- `pet:set` 只改内存里的目标值，不推快照 —— 尺寸由逐帧的 `pet:size` 送达；
- 尺寸动画期间渲染进程**不再上报** metrics，主进程按「实测宽度 × 尺寸比例」线性外推，
  动画结束后再回报精确值。

实测：一次 40 → 96 的满量程拖动，主进程 `/state` 往返延迟 160 个采样
`min 1 / median 10 / p90 18 / max 46 ms`，**没有一个样本超过 50 ms**；日志里的尺寸是
`40 → 62 → 86 → 96` 这样逐帧插值，不是一步跳过去。

### 拖动悬浮球为什么交给主进程

拖动一开始也放在渲染进程：`mousedown` 后每个 `mousemove` 发一次 IPC 让主进程挪窗口。
这是错的 —— 鼠标的报告频率远高于「挪动一个大的透明窗口」的速度，窗口会**越拖越落后**：
球从光标下面溜走，光标于是不停地在「抓取」和「箭头」之间跳，看起来就是球和鼠标一起闪。
实测一次 1.4 秒的横扫，球最终停在 1209 物理像素处，而鼠标已经在 1500。

现在渲染进程只负责**判断这次按压是点击还是拖动**（位移超过 4 px 即为拖动），
真正的跟随交给主进程：它本来就在为悬停判定每帧读一次真实光标位置
（`screen.getCursorScreenPoint()`），顺手用同一份数据驱动窗口即可 —— 每帧一次
`getCursorScreenPoint` + 一次 `setBounds`，**循环里完全没有 IPC**。
实测同一次横扫，窗口 x 一路跟到 1389（目标 1395），球稳稳待在光标下。

渲染进程把按压分成三个阶段报给主进程（`pet:drag(active, moved)`）：
`按下` 时就开始跟随（球立刻跟手，不差那几像素），`位移超过 4px` 时才算「拖动成立」
（此刻**收回灵动岛并关掉设置面板**），`松开` 时灵动岛展开回来并写盘。所以**单纯的点击
不会误触发拖动那套逻辑**。

### 八处让拖拽手感变差的细节

1. **按住不动时球在震，而「加死区」是错的解法。** 跟随循环一秒几十次，真实鼠标即使手不动
   也会有约一个像素的抖动，直接照单执行就是高频震动。第一版加了 2px 死区 —— 静止是不震了，
   但慢速拖动被切成 3px 一跳的顿挫，**抖动只是换了个形式**。
   现在的做法是**一欧元滤波（One Euro filter）**：截止频率随估计速度自适应，
   指针几乎不动时重度平滑（抖动消失），快速拖动时几乎不滤波（不产生橡皮筋拖尾）。
   这是指针跟踪领域的标准解法。
   - 静止 + 人为注入 ±1px 抖动：60 个采样，球只在一个 **2×2 DIP** 的方框里动
     （那是窗口坐标取整在相邻两个像素之间翻，肉眼不可见）—— 而手抖本身就有 ±0.67 DIP
   - 慢 / 中 / 快三档拖动：**回退次数全部为 0**（没有来回抖）

   **滤波器的「速度估计」本身也在被滤波，这一层没调好就会在加速和反向时掉队：**

   ```js
   const SMOOTH_DERIV_CUTOFF = 1.0;   // tau 约 160ms —— 太慢
   ```

   手已经反向甩回来了，速度估计还在报「正往右冲」，于是截止频率迟迟不升高、球继续被重滤波
   —— 表现就是**拖快了跟不上手**。调到 **3.0 Hz（tau 约 53ms）** 后实测：

   | 场景 | 释放前一刻球落后光标 |
   |---|---|
   | 40 px 球，3750 DIP/s 硬反向 | **0 DIP** |
   | 96 px 球，3750 DIP/s 硬反向 | **0 DIP** |
   | 40 / 96 px 球，5625 DIP/s 硬反向 | **0 DIP** |

   **而「一松手就闪现到光标」是另一个独立的 bug**：释放时走的是**原始**光标坐标，
   等于丢掉滤波器的全部状态、直接把球瞬移到光标上 —— 那一刻落后多少就闪多少。
   实测反向甩动后释放会瞬移 **2~4 DIP**，手越快越明显。

   现在释放**不再瞬移**：保留滤波值，并让跟随循环多跑一小会儿（`DRAG_SETTLE_MS = 260`），
   把最后那点距离**滑**过去，追上即停或超时即停。实测释放后的落点轨迹 `0 0 0 0 0 0`，
   单帧最大位移 **0 DIP** —— 没有任何跳变。
2. **采样率要高于屏幕刷新率。** 原来的跟随定时器是 16ms，而 60Hz 屏幕是 16.7ms 一帧 ——
   两者会拍频，于是有些帧拿到两个陈旧样本、有些帧一个都没有，看起来就是一顿一顿。
   现在 **8ms**：鼠标本身是 125~1000Hz 上报的，采样远高于刷新率。
3. **长按一被识别就立刻收回。** 原来有两道门槛：渲染进程位移 4px 才算拖动，主进程还要再等
   **球**移动 6px 才收岛。加上死区之后第二道门槛可能要好几帧才满足，于是「开始拖了、岛还挂着」。
   现在第二道门槛删掉，`moved` 一到就收岛。
4. **贴边要贴得住，又不能掉出屏幕。** 夹取范围是**所有显示器工作区的并集**再各边内缩
   一个球半径：球可以正好停在屏幕边缘（边缘检测 → 停住），但绝不会有一半吊在屏幕外。
   用并集而不是逐屏判断，是为了让跨显示器的接缝处不会卡顿或跳一下。
   实测六个方向的越界请求，落点分别是 `(28,800)`、`(1679,800)`、`(800,28)`、`(800,991)`、
   `(28,28)`、`(1679,991)` —— 全部恰好贴边且完整可见。
5. **拖动中「时不时闪现」的元凶：面板朝向没锁住。** 球靠近屏幕顶部时设置面板改从下方弹出，
   这个标志决定球画在窗口的**顶部还是底部**；而渲染进程只有在收到完整快照时才会知道它变了
   —— **拖动期间根本不推快照**。现在窗口和球的位置都不再依赖这个标志，问题从结构上消失。
6. **方向翻转的必要条件写得太松。** 现在方向是**锁定**的：球在手上时绝不翻；即使翻，
   也必须越过中线 `SIDE_HYSTERESIS`（80 DIP）才生效，避免停在屏幕正中间时来回抖。
7. **面板翻到下方时，球的位置算错了。** 球靠近屏幕顶部时设置面板改从下方弹出，此时主进程是
   **按球在窗口顶部**来摆放窗口的；可是样式表里 `.pet` 一直写着 `bottom: var(--pad)`，
   把球钉在窗口**底部**。两者差了一整个面板高度（实测 259 DIP），拖起来就像在跟手打架。
   实测修复前后从上半屏起拖同一段距离，落点误差从 **250 DIP** 降到 15 DIP。
8. **每帧一次 `win.getBounds()`**（一次原生往返）也去掉了，改成自己记住上次写入的盒子；
   每 800 ms 一次「拖动后写盘」也改成**拖动期间完全不落盘** —— `store.save()` 是同步写文件，
   落在拖动中途就是一次可见的卡顿。

### 拖动时只剩球：不缩放窗口

按住拖动时，灵动岛和设置面板**一起消失**，屏幕上只剩球本身，松开后灵动岛展开回来、
设置面板保持关闭（它是被这次拖动收走的）。

原来这里还多做了一件事：拖动期间把窗口缩成一个只包住球的小方块，想着让合成器少搬点面积。
**这是错的，而且是「松开后球会闪」的来源** —— 缩放一个透明窗口本身就会闪：
拖动开始时缩一次、结束时涨回来一次，一次拖动闪两下。现在窗口**只在启动时建一次**，
之后永远只挪位置、不改尺寸。

好处不止是不闪：窗口尺寸不再随球径、不再随拖动、也不再随面板开合变化，于是球在窗口里的
位置在**任何状态下都是同一个**，主进程和样式表之间没有任何需要对齐的东西。

### 面板的测量值不能用 getBoundingClientRect

面板关闭时带着 `transform: translateY(10px) scale(0.965)` 的入场变换，而
`getBoundingClientRect()` **把变换算进去** —— 同一块面板，开着量是 250px，关着量是 241px。
主进程是拿这个数字去算窗口高度的，于是**面板每开合一次窗口就缩放一次**，又是两次闪。
改用 `offsetWidth` / `offsetHeight`：它只反映布局，不带变换，数值恒定。

### 球在窗口里的位置是固定的

这是整套布局的核心。

窗口按「**最大的球 + 任意一侧的灵动岛或设置面板**」定尺寸，球本身横向钉**外侧边**、
纵向钉**上沿**：

```
        ┌──────────────────────────────────────────┐
        │            ← room →   ↑ panelReserve      │
        │   [设置面板]  ●球→     [灵动岛展开]        │
        │            ← room →   ↓ panelReserve      │
        └──────────────────────────────────────────┘
```

**横向钉「外侧边」（不是球心）。** 外侧边就是**设置面板贴着的那条边** —— 灵动岛朝右展开时
是球的左边缘，朝左展开时是球的右边缘。钉住它有两个直接后果：

- 球只能**朝内侧长**，于是它和面板的边缘在**任何球径下都严丝合缝**；
- 面板本身一个像素都不动。

如果改成钉球心（试过），球就会往两边一起长：球径 40 时球比面板边缘内缩 28 DIP，
而 28 DIP 占了小球宽度的 **70%** —— 看着就是没对齐。

**代价：换边时窗口要挪 —— 这是一个绕不开的三选二。**

- (N1) 球的外侧边**在每个球径下都与面板齐平** ⟹ 外侧边必须是固定点
- (N2) 缩放时**面板不动** ⟹ 面板也必须锚在固定点上
- (N3) 换边时**窗口不动** ⟹ 球在窗口里的位置不能随朝向改变

(N1) ∧ (N2) 要求外侧边固定，而外侧边对右展开是球的**左**边、对左展开是球的**右**边 ——
所以球在窗口里的位置**必然**随朝向改变，**与 (N3) 直接冲突**。
（除非球绕中心长，那 (N1) 就没了；或者面板跟着球边跑，那 (N2) 就没了。）

**选择：保住 N1 和 N2，把 N3 的位移压到最小并补掉。**

位移量是 `|mid − size|`，而窗口建在哪个 `mid` 上是可以选的。把 `mid` 放在**尺寸区间的正中**
（68）而不是原先的房间边界上：

| 球径 | 40 | 56 | 72 | 96 |
|---|---|---|---|---|
| 换边时窗口位移 | 28 | **12** | 4 | 28 |

（放在房间边界时是 56 / 40 / 24 / 0 —— 最坏情况翻倍，而且默认的 56 px 正好在不好的那一端。
对比最早「固定边 + 窄窗口」那版的 **366 DIP**，小了十几倍。）

**剩下的那一帧错位也被补掉了**，见下一节。

**纵向钉「上沿」**，所以球向下长，上方的面板不会动。

于是**窗口位置不再依赖任何会变的东西**：

| 变化 | 以前会影响 | 现在 |
|---|---|---|
| 球径 | 窗口尺寸、球在窗口里的位置 | 都不变（球只往内侧长） |
| 面板翻到下方 | 窗口纵向跳 + 球挪窝 | 纯 CSS |
| 拖动开始/结束 | 窗口缩放 | 不变 |
| 灵动岛换边 | 窗口横向跳 366 DIP + 球挪窝 | 窗口横移 ≤ 28 DIP，且那一帧被补掉 |

**为什么窗口尺寸绝对不能变 —— 残影的成因。** 拖动时把窗口缩成小球方块、松手再涨回来，
每次拖动就闪两下；面板开合时若窗口跟着变，又是两次。现在窗口**只在启动时建一次**。

球在窗口里的位置也不再依赖面板朝向、拖动状态、灵动岛宽度 —— 只剩「外侧边」这一个锚点。

代价是窗口是 `860×908`。它是全透明的置顶窗口，不参与命中测试
（点击穿透由 `setIgnoreMouseEvents` 按悬停区域控制）。

### 换边那一帧的错位是怎么补掉的

窗口位置由主进程的 `setBounds` 决定，球在窗口里的位置由 CSS 变量决定 —— **两条路，一个帧边界**。
换边时两者都要变，谁先到都会让中间那一帧把球画偏 `|mid − size|`，也就是拖动越过屏幕中线时
看到的「往左/往右闪」，而且**球越小偏得越多**（因为 `|mid − size|` 随球变小而变大）。

两道保险：

1. **主进程不许抢跑。** `commitWindowBox()` 在发现球在窗口里的位置要变时，先把新布局发给
   渲染进程，**窗口按住不动**，等渲染进程回话「新摆法已经上屏」才 `setBounds`
   （另有 150 ms 超时兜底，防止消息丢了把宠物冻住）。顺序永远是「先换摆法，再挪窗口」。
2. **渲染进程自己补那一帧。** 收到新摆法时窗口还没挪，于是按
   `dx = 球该在的位置 − (window.screenX + 新摆法)` 把球先平移过去；`window.screenX` 是浏览器
   自己记的窗口位置，所以窗口一真的动了，`dx` 就归零、平移自动撤掉。

**这个平移是「一次性按住」，不是每帧重算**：这期间球还在被拖动，每帧重算会因为目标值过期
而越补越多 —— 实测那样会算出 −550 DIP 的「修正」，把球往反方向拽。现在只在换摆法那一帧算一次，
之后盯着 `window.screenX`，一变就撤（最多等 8 帧）。

实测：一次同侧拖动（不换边）触发的修正次数为 **0**；换边时按 `|mid − size|` 的量级补一次。
拖动跟手误差在球径 40 / 56 / 96 下**最大 2 DIP**。

### 设置面板的宽度 = 整个灵动岛的最大长度（含球）

灵动岛是**球 + 展开出来的那一截**，所以「灵动岛的最大长度」= 最大球径时的**整条胶囊**。
面板宽度现在就是这个数。

当前球径不是最大时，怎么知道最大球径下有多宽？**临时把 `--s` 换成最大球径量一次，再换回来**
—— 整段在同一个同步块里完成，中间状态不会被绘制，那次强制重排正是目的所在。

```js
const previous = root.style.getPropertyValue('--s');
root.style.setProperty('--s', `${frameSize}px`);
const w = Math.ceil(islandInner.getBoundingClientRect().width);
root.style.setProperty('--s', previous || `${renderedSize}px`);
```

**光有测量还不够，还得让它稳定。** 灵动岛长度取决于里面的文字（运行时间会从 `9秒` 一路涨到
`1时 2分 3秒`），所以测得的值**只增不减**（否则面板每秒抖一下），但也不能无限增长
（一旦超过窗口预留的空间，窗口就得缩放，而**缩放透明窗口必然闪一下**）。
于是把窗口预留的空间改成**纯常量**（`frame × ISLAND_ALLOWANCE`，与任何测量无关），
并且**把灵动岛本身也钉在这个上限内**。这样窗口从建好那一刻起尺寸就再也不会变，
而面板 = 球的直径 + 灵动岛的上限 = 预留空间，两边天然相等。

实测（球径来回扫 96 → 56 → 40 → 96 → 56 → 40）：

| 观测量 | 结果 |
|---|---|
| 窗口尺寸取值数 | **1** —— 全程 `860x908` |
| 面板宽度 | **324**（恒定） |
| 球径 96 时的胶囊 | 96 + 228 = **324** ✓ 与面板完全相等 |

### 贴边时缩放为什么会「整块界面往右移」

**现象**：球停在屏幕最边缘（或角落）时拉伸大小，整块界面（球 + 灵动岛 + 面板）会先往屏幕里
跳一下，再慢慢挪回去 —— 看着像不稳定。

**成因**：夹取函数用的是**目标的**球径，不是**当前的**球径。

```js
// 错的：一开始缩放就按最终尺寸要空间
const half = Math.max(store.data.ballSize, renderedSize) / 2;
```

球停在左边缘时它的球心正好在 `size / 2`（夹取下限）。请求放大到 96 的那一刻，
夹取立刻要求 `centre ≥ 48`，于是整个界面被推进屏幕里 28 DIP —— **而球当时还只有 40 宽**，
根本没有长到需要这块空间。之后动画追上来，界面再慢慢挪回去。这就是那一下「往右移」。

更糟的是它还在和 `shiftCentreForSize` 打架：那个函数靠「球心移动半个增量」来钉住外侧边，
而夹取要求的是同一件事 —— **用当前尺寸时两者逐像素相等，谁都不用动；用目标尺寸时夹取
单方面压过来，锚点就废了。**

**修法**：夹取一律按**当前实际球径**算。

```js
const half = (renderedSize || store.data.ballSize) / 2;
```

实测：把球顶到四个边和四个角，各来回拉伸三次，边采样边看：

| 位置 | 球的外侧边 | 面板位置 | 球的顶边 |
|---|---|---|---|
| 左边缘 | **1 个值** `0` | 1 个值 | 1 个值 |
| 右边缘 | **1 个值** `1706` | 1 个值 | 1 个值 |
| 上边缘 | 1 个值 | 1 个值 | **1 个值** |
| 下边缘 | 1 个值 | 1 个值 | 4 个值（见下） |
| 左上 / 右上 | **1 个值** | 1 个值 | 1 个值 |
| 左下 / 右下 | **1 个值** | 1 个值 | 4 个值（见下） |

**水平方向处处钉死**，一个像素都不动。

**下边缘那一列是唯一的例外，而且是必须的**：球已经贴着屏幕底部，再往下长就出屏了，
所以球底被钉住、球往上长（实测球底恒为 `718`，球顶从 `678` 单调升到 `622`，
`678 − 622 = 56 = 96 − 40`，正好等于长出来的那一截）。上方的设置面板跟着升 ——
这是「球不出屏」的唯一解，而且它是**跟着生长平滑推进**的，不是跳变。

### 设置面板和球怎么对齐

规则一句话：**面板贴着球的外侧边，而球的外侧边是钉死的，所以两者在任何球径下都齐平。**

| 灵动岛在 | 齐平的是 | 球往哪边长 |
|---|---|---|
| 右侧 | 面板的左边缘 = 球的左边缘 | **向右**（左边缘不动） |
| 左侧 | 面板的右边缘 = 球的右边缘 | **向左**（右边缘不动） |

三个关键点，都是踩过坑才定下来的：

**① 对齐的是「外侧边」。** 一开始左侧那半边把面板的**右边缘**对到了球的**左边缘**，
于是整块面板挂在球的外侧，球孤零零探在外面 —— 右侧看着正常，左侧就不对。

**② 锚点必须是常量，而且必须就是球自己钉的那条边。** 这两件事是同一件事：
球横向钉外侧边，面板就贴这条边。于是「球长、边缘不动」和「面板不动」自动同时成立。

**③ 用「外侧边」而不是「最小球径时的边缘」定面板。** 曾经把面板锚在「某个固定球径下的
球边」上（试过最大、也试过最小）—— 那样面板确实不动，但球会**往两边一起长**，
于是除那一个球径之外全都对不齐：锚在最大时，球径 40 时内缩 28 DIP（占球宽 70%）；
锚在最小时，球径 96 时外探 28 DIP。**只要球是绕中心长的，就不可能一直对齐。**

实测球径 40 / 56 / 72 / 96 来回切换：

| | 球的外侧边 | 面板边缘 | 齐平误差 |
|---|---|---|---|
| 灵动岛在右 | `352` 全程不变 | `352` 全程不变 | **0 / 0 / 0 / 0** |
| 灵动岛在左 | `1298` 全程不变 | `1298` 全程不变 | **0 / 0 / 0 / 0** |

纵向同理：面板锚在球的上沿（`--ball-y`，常量），球向下长，面板不动。

### 调整大小时为什么面板不动、也不抖

球钉在固定点上（横向外侧边、纵向上沿），所以它长大时是**从上沿往下、朝内侧长**。
面板锚在常量上，所以拖动滑块时它纹丝不动。

实测球径来回扫过 **49 个中间尺寸**：

| 观测量 | 取值数 |
|---|---|
| 窗口几何（位置 + 尺寸） | **1** —— 全程 `860x908` |

顺带把尺寸动画本身也做稳了：

- **缓动改成按实际经过的时间算**（`1 - exp(-dt/τ)`）而不是「每帧走剩余量的 26%」。
  原来的写法对掉帧过敏 —— 某一拍晚了，球就会多跳一截；现在 60Hz 还是 120Hz 观感一致。
- 计时器 **16ms → 8ms**，理由和拖动那边一样：16ms 与 60Hz 的 16.7ms 会拍频。
- 收尾阈值内**吸附到目标值**，避免指数曲线那条永远走不完的长尾。

顺带修掉一个一直在烧 CPU 的 bug：尺寸动画结束时只把 `sizeTimer` 变量置空、
**没有 `clearInterval`** —— 定时器继续每 16ms 跑一次完整布局 + 两次 IPC 推送，直到进程退出。
只要拖过一次滑块，这个循环就再也不会停。实测修复后一次缩放结束后的 5 秒空闲里，
主进程只消耗 **0.09s** CPU。

### 灵动岛变短：grow-only 的门闩要放对地方

灵动岛展开期间宽度是**只增不减**的（`Math.max`）：运行时间每秒从 `9秒` 变成 `10秒`，
宽度跟着变会让整条胶囊抖。但这个门闩**不能跨球径变化** —— 否则球从 96 缩到 40 时，
灵动岛还记着最大那次的长度，怎么都不肯变短。

现在门闩只在**球径没变**时生效：球径一变就把记录清零重新量。实测（鼠标停在球上）：

| 球径 | 实测灵动岛长度 |
|---|---|
| 96 | 227 DIP |
| 72 | 195 DIP |
| 56 | 175 DIP |
| 40 | 119 DIP |

同时给灵动岛宽度加了一道**上限**（不超过窗口为它预留的空间），免得某次测量偏大时
把它画到窗口外面去。

### 「灵动岛常驻展开」为什么放在主进程做

设置面板里多了一个开关：开启后灵动岛一直展开。

实现上**没有加第二条状态**，而是改了 hover 状态机的一条分支。灵动岛的开关本来就只有主进程
说了算（悬停是主进程轮询真实光标决定的），所以只要在这台状态机里加一个「不需要悬停」的模式：

```js
const pinned = store.data.islandPinned === true;
// 常驻展开：不需要悬停，岛就在那儿
if (pinned && !islandOpen && !hoverSuppressed) { islandOpen = true; pushHover(); }

if (engaged) { ...悬停打开... }
else if (pinned && !panelOpen) { outsideSince = 0; }   // 没东西要收，什么都不做
else { ...离开 220ms 后收起（pinned 时只收面板，不收岛）... }
```

三个刻意的取舍：

- **只影响灵动岛，不影响设置面板。** 面板照旧：点齿轮打开、指针离开就收。所以那个
  `else if` 只在**面板没开着**时才跳过收起逻辑 —— 面板开着时仍然走正常流程，
  只是到点只收面板、不收岛。
- **拖动照旧什么都不留。** 拖动那条路径本来就把岛和面板一起清掉（`pet:drag`），
  它跑在 hover 状态机之前，所以常驻展开不会让拖动时拖着一整条岛。松手后岛自己回来。
- **不做成第二条渲染状态。** 渲染进程只是照着 `pet:hover` 画，多一个状态就多一处要同步 ——
  而这个开关的语义恰好就是「把悬停这条件去掉」，正好是状态机里改一行的事。

**实测**：

| 场景 | 结果 |
|---|---|
| 开启后指针停在屏幕另一头 | `islandOpen=True` 持续保持 |
| 指针移到岛上 | 仍然 `True`，不抖 |
| 拖动中 | `islandOpen=False panelOpen=False`（照旧全清） |
| 松手后 | `islandOpen=True` 自动回来 |
| 开关关掉、指针移开 | `islandOpen=False`，回到原来的悬停行为 |
| 点开关 | 立刻写进 `preferences.json`（`"islandPinned": false`），重启后保持 |

### 灵动岛展开时的背景动画

灵动岛展开后，岛内背景会有一点**水下的动静**：几颗气泡慢慢上浮、一道很淡的光带扫过，
每隔一阵子还有一只小鲸鱼从左往右游过去。取材自鲸鱼娘本身 —— 蓝白配色、水下、鲸鱼。

**刻意的分寸**：这是背景，不是主角。气泡最大只有球径的 9%、峰值不透明度 0.72；
鲸鱼不透明度 0.16；光带 0.15。全部在文字**下面**，两行数字的清晰度一点不受影响。

**两个必须显式处理的坑**（都是看截图才发现的）：

1. **`.island` 只有文字那么高。** `.capsule` 是 `align-items: center`，所以 `.island`
   这个 `overflow: hidden` 的裁剪框只有文字那一条 —— 气泡画出来了，但**全被裁在文字带里**。
   改成 `.island { align-self: stretch; display: flex; align-items: center }`：
   文字位置不变，裁剪框变成整条胶囊。
2. **动画层也跟着要显式给高度。** 同理，`inset: 0` 只会得到那条窄带子；改成
   `top: 50%; height: var(--s); transform: translateY(-50%)`，按球径撑满胶囊。

**不打断布局**：整个动画层是绝对定位的，不参与 flex 布局，所以量灵动岛宽度
（`island-inner` 的 `max-content`）完全不受影响 —— 这一点很关键，窗口宽度和悬停区域都靠那个数。

**不白烧 CPU**：岛收起时宽度为 0、本来也看不见，所以 `.capsule:not(.open) .island-fx`
连同它的子元素一起 `animation-play-state: paused`。

**设置**：面板里的「灵动岛展开动画」开关，写进 `preferences.json` 的 `islandFx`（默认开）。
关掉时给 `#stage` 加一个 `fx-off` 类，`.island-fx { display: none }`。
另外尊重系统的 `prefers-reduced-motion`。

**实测**（取岛底部一条不含文字的窄带，连拍 6 帧比哈希）：

| 设置 | 结果 |
|---|---|
| 开 | 6/6 帧各不相同 ⟹ 在动 |
| 关 | 1/6 ⟹ 完全静止 |
| 再开 | 3/6 ⟹ 在动 |

### 自定义悬浮球图标（含 GIF）

设置面板里的「悬浮球图标」：**选择图片…** 打开系统文件对话框，**恢复默认**回到内置立绘。
支持 GIF 动图与 PNG / JPG / WebP / BMP。

**几个刻意的决定：**

- **只存路径，不复制文件。** 用户挑的图放在哪儿就留在哪儿。代价是文件被移走/删掉之后图标会
  回到默认 —— 但那比留一个破图好，而且用户能看懂发生了什么。`ballImageUrl()` 每次快照都
  `stat` 一下（结果按路径缓存，只在换图时才重新读一次文件头）。
- **按文件头判断，不看扩展名。** `sniffImage()` 读前 16 个字节认 PNG / JPEG / GIF / WebP / BMP
  的魔数。这样把视频改名成 `.png` 会被挡下并提示，而一个名字不对但确实是图片的文件照样能用。
  这个检查在**选图时**和**每次解析快照时**都做 —— 后者是为了手改过的 `preferences.json`
  也不会把球弄成破图。
- **文件对话框不挂父窗口。** 悬浮球是 `focusable: false`，挂在一个拿不到焦点的窗口上的模态框
  是用户点不到的对话框。
- **CSP 放开 `img-src file:`。** 选中的图在任意路径上，渲染进程又要用 `<img>` 显示它。
  渲染进程没有任何远程内容、也不做导航，所以这个放开是可控的。
- **GIF 不需要任何额外代码** —— `<img>` 自己会播。测试用的那张 12 帧 GIF 在球上实测
  连拍 6 帧**帧帧不同**。
- **`applyBallImage()` 会比较新旧 URL**，避免每秒一次的快照把 GIF 从头重播。
- **自定义图用 `object-fit: cover` 铺满整圆**；内置立绘那套 96% + 下移 1% 是给那张立绘量的，
  换任意图片会露底或偏心。

**实测**（把 `preferences.json` 的 `ballImage` 分别指向不同文件再启动）：

| prefs 指向 | 解析结果 |
|---|---|
| `test-ball.gif` | 用上了（且连拍 6 帧都在动） |
| `test-ball.png` | 用上了 |
| `fake.png`（其实是文本） | **拒绝** → 回默认立绘 |
| 不存在的路径 | **拒绝** → 回默认立绘 |
| `null` | 默认立绘 |

### 熄屏再亮屏之后球就点不动了

**现象**：挂机一段时间，屏幕自动熄掉，再亮起来之后 —— 球还在、还能看见，但**拖不动，
点球和点齿轮都没反应**。

**根因（日志抓到的，不是猜的）**：屏幕关闭期间，`screen.getCursorScreenPoint()` 返回的不是坐标，
而是一个**哨兵值**：

```
poll local=(-954437404,-954437414)   ← 熄屏期间的"坐标"
```

主进程拿它去算「指针在不在球上」，结论永远是**不在** —— 于是把窗口切成
`setIgnoreMouseEvents(true)`（点击穿透）✗。屏幕亮起来之后这个状态**就一直是穿透**，
因为亮屏后第一次轮询拿到的仍是坏值、或者状态已经被扣住了 ✗ ——
球看得见、点不到、拖不动、齿轮也点不开 ✓ 完全对上症状。

**两层修法：**

1. **不理会不可能的坐标**（治本，且不依赖任何事件）：

   ```js
   if (!Number.isFinite(pointer.x) || !Number.isFinite(pointer.y)
     || Math.abs(pointer.x) > 1e6 || Math.abs(pointer.y) > 1e6) return;
   ```

   跳过这一拍，指针模式**保持原样** —— 坏值再也不会把球切成穿透。

2. **电源/显示器事件后整体重来一遍**（治那些坏值之外的情况）：

   `powerMonitor` 的 `resume` / `unlock-screen`，加上 `screen` 的
   `display-added` / `display-removed` / `display-metrics-changed`，
   统一走 `recoverAfterWake(reason)`：清掉缓存的工作区、重新解析所在显示器、
   重新夹取位置、重新 `setAlwaysOnTop` + `moveTop`、用 1 像素的尺寸抖动逼 Chromium
   重新合成、把指针模式缓存清空让下一次轮询从头判定。

   另外加了一条启动开关：

   ```js
   app.commandLine.appendSwitch('disable-features', 'CalculateNativeWinOcclusion');
   ```

   Chromium 会把「被遮住」的窗口停止绘制，而熄屏会让所有窗口都看起来被遮住，
   这个追踪器并不总能干净地恢复。这个窗口本来就是要盖在一切上面的，这个计算没有收益。

**实测**（真的用 `SC_MONITORPOWER` 熄屏 5~6 秒再亮回来）：

| | 结果 |
|---|---|
| 熄屏期间日志 | `poll ignoring implausible cursor position (-954437248,-954437248)` |
| 亮屏时日志 | `recover resume` / `recover unlock-screen` |
| 亮屏后指针移开 | `islandOpen=False` |
| 亮屏后指针停在球上 | `islandOpen=True` ✓ **能正常响应** |
| 窗口几何 | 前后完全一致（1 像素抖动已还原） |

> 顺带一个教训：验证这件事必须真的熄屏，而**熄屏会把机器留在锁定/桌面不可用的状态** ——
> 之后连 PowerShell 都起不来（`0xC0000142`，`STATUS_DLL_INIT_FAILED`）。
> 这类测试应当先问过用户再做，而不是自己反复关别人的屏幕。

### 指针一离开，界面一起让开

设置面板是**挂在灵动岛（胶囊）上**的，两者原来各有一个独立的关闭计时器（面板 750ms、
灵动岛 150ms）—— 于是指针离开后，灵动岛先收，面板孤零零地悬在半空。

现在**一个计时器、一起收**：指针离开任何区域后 **220ms**，灵动岛和面板在同一个
`pushHover()` 里同时关掉。220ms 而不是 0，是为了让一次偶然的采样失误不至于把界面闪关再闪开。
收起方向的动画也比展开快（灵动岛 0.34s → 0.19s，面板 0.30s → 0.17s）：让开位置要干脆。

实测时间线（同一场景，前后对比）：

| | 修复前 | 现在 |
|---|---|---|
| 面板消失 | 864ms | **284ms** |
| 灵动岛消失 | 1129ms | **284ms** |

同时确认了「停着不动不会被误关」：指针停在球上 2 秒、或者移到展开的灵动岛上 1.5 秒，
都远超 220ms，界面依然保持展开。

### 一个 Electron 的坑：`setPosition` 会偷偷改宽度

拖动时的跟随循环原来用 `win.setPosition(x, y, false)` 只挪位置。实测在**透明窗口**上，
它会让宽度一路漂移：一次拖动里从 180 DIP 长到 211 DIP（高度倒是没变）。
现在改成每帧写完整的 `setBounds` —— 窗口尺寸是恒定的，重写一次没有额外代价，
但宽度不会再漂。

### 为什么没有投影

胶囊和设置面板原来都带 `box-shadow: 0 14px 34px rgba(0,0,0,.52)` 这类投影。在**透明置顶
窗口**上，投影并不会落成「窗口的阴影」，而是直接糊在后面的桌面或别的窗口上，看起来就是
悬浮球外面糊了一圈灰。现在改成只留一圈 1px 的描边 + 内侧高光：深色和浅色壁纸上都还看得清
轮廓，但不再往桌面上投任何东西。实测球右侧 4~44px 的亮度是**平的 255**，
球下方也只有边缘抗锯齿造成的 4.6/255 差异。

### 灵动岛换边为什么不再「先收再展」

球心越过屏幕中线时，命中框会跟着换到球的另一侧，理论上**可能有一帧光标落在新的胶囊框
之外**，让灵动岛收起又立刻展开。

不过现在这件事已经不可能发生了：球在窗口里的位置是固定的，换边**不移动任何东西**
（见上面「球在窗口里的位置是固定的」），窗口和命中框都不会跳。收起那 220ms 的延时
同时也是一道保险。

### 窗口唤起为什么只做「加法」

`focusDshStrong` 里对窗口状态的处理是刻意最小的：先用 `GetWindowPlacement` 看 `showCmd`，
**只有确实被隐藏（`SW_HIDE`）才 `SW_SHOW`，只有确实最小化（`IsIconic`）才 `SW_RESTORE`**，
其余情况一律不碰显示状态，只做 `SetForegroundWindow` + `BringWindowToTop` + `SetFocus`，
最后用 `GetForegroundWindow() == h` 校验。原因很简单：一个只会「显示/前置」的函数不可能
把窗口关掉，而随手调 `ShowWindow` 正是各种意外状态的来源。

### DSH 已经在前台时，点球什么都不做

**现象**：DSH 已经打开并且就在最前面，这时点悬浮球，任务栏里的 DSH 图标会**闪红**
（Windows 的「需要提醒」闪烁）。

**成因**：`SetForegroundWindow` / `BringWindowToTop` / `SetFocus` 这几个调用，作用在一个
**本来就在最前面**的窗口上时，Windows 会用「闪任务栏按钮」来回应 —— 也就是那个红闪。

**修法两条**：

1. **入口直接短路。** `Force()` 第一句就是：

   ```csharp
   if (GetForegroundWindow() == h && IsWindowVisible(h) && !IsIconic(h)) return "already";
   ```

   已经在前台就**一个 API 都不调**，连 `ShowWindow` 都不碰。

2. **让球根本不去抢焦点。** 悬浮球窗口加了 `focusable: false`：点击它不会把前台从用户
   正在用的窗口那里夺走。这一步很关键 —— 否则「点球 → 球抢走焦点 → 再还给 DSH」本身就
   是一次多余的激活，照样会闪。

实测四种状态：

| DSH 状态 | 点击悬浮球后 | 走了哪条路 |
|---|---|---|
| **已经在前台** | **完全没反应**（仍是 `fg=True`） | `reason:"already"` —— 零 API 调用 |
| 被别的窗口挡住 | 提到最前 | `reason:"focused"` |
| 最小化 | 还原并前置 | `reason:"focused"` |
| 关到后台（隐藏） | 重新显示并前置 | `reason:"focused"` |

`pet.log` 里现在会写明是哪一种：`open-dsh -> focused 已经在前台，未做任何操作`。

### 关到后台再打开：为什么要让 DSH 自己来开

**现象**：点右上角的 X 把 DSH 关掉（窗口隐藏、程序留在后台），再点悬浮球 ——
窗口是回来了，但**页面是死的**（看着还是点叉那一刻的样子）。

**根因（读 DSH 自己的源码找到的）**：DSH 处理 X 用的是 Electron 的 `win.hide()`。
关键在于 **渲染进程的「可见性」来自 Electron 的记账，不是 OS 的窗口状态** ——
所以窗口被 `SW_HIDE` 之后，页面里的 `document.hidden` 一直是 `true`，**它的 JS 被节流停住了**。

这就解释了一个很容易误判的现象：**画面其实在正常重绘**（我拿「标题栏按钮悬停高亮」验证过，
像素确实在变），但**页面里的逻辑是停的** —— 因为悬停高亮是 CSS，不走 JS。
所以我一开始以为「窗口冻住了」是错的，真正冻住的是页面的 JS。

**外面的任何调用都救不回来**：`ShowWindow` / `RedrawWindow` / `SetWindowPos` 只能改 OS 窗口，
改不了 Electron 的记账 ✗。DSH 自己的恢复路径是它源码里的：

```js
focusPrimaryWindow = () => {
  ...
  if (window === mainWindow && !enteredWorkspace) return;
  if (window.isMinimized()) window.restore();
  window.show();      // ← 真正的 win.show()
  window.focus();
};
```

托盘图标的「打开」调用的就是它 —— 而**托盘的图标是可以从外面点的**。这是整件事的转折点。

#### 怎么从外面点 DSH 的托盘图标

DSH 的托盘是 Electron 的 `Tray`，它在 DSH 进程里建了一个隐藏窗口，类名固定：

```
hwnd=1377344  class="Electron_NotifyIconHostWindow"
```

托盘图标被点是**通过窗口消息**送到这个窗口的，所以只要照着协议发一条就行。
协议从 Electron 源码 `shell/browser/ui/win/notify_icon_host.cc` 里抄：

```cpp
const UINT kNotifyIconMessage = WM_APP + 1;   // 0x8001 —— 注意不是 WM_USER+1
const UINT kBaseIconId = 2;                   // 图标 id 从 2 开始
UINT NotifyIconHost::NextIconId() { return kBaseIconId + next_icon_id_++; }
// 而且左键是 WM_LBUTTONDOWN（0x0201），不是 WM_LBUTTONUP
```

所以一次「点托盘图标」就是：

```csharp
SendMessage(trayHostWnd, 0x8001, (IntPtr)iconId, (IntPtr)0x0201);
```

**我一开始三个参数全猜错了**（`WM_USER+1` / id 从 1 开始 / `WM_LBUTTONUP`），连试 16 种组合都不动 ——
因为猜错的消息号会被 `DefWindowProc` 静静吃掉，看不出任何区别。

**现在焦点脚本的做法**（只在「窗口原本是隐藏的」这条路上）：

1. 找到 DSH 进程里那个 `Electron_NotifyIconHostWindow`；
2. 依次用 id `2..5` 发 `0x8001 + WM_LBUTTONDOWN`（哪个 id 属于它从外面看不出来，
   而发到没有图标的 id 上 Electron 直接忽略，所以顺序试是安全的）；
3. 每发一次看一眼窗口是否出现，出现就停；
4. 都不行才退回到 `SW_SHOW` + `Wake`。

焦点脚本现在有三种成功返回值，主进程据此决定走哪条路：

| 返回值 | 含义 | 实际动作 |
|---|---|---|
| `already` | 本来就在最前 | **什么都不做**（避免任务栏闪红） |
| `focused` | 只是被挡住或最小化 | 前置即可 |
| `shown` | **原本是隐藏的** | **点 DSH 的托盘图标**，让它自己 `win.show()` |

**实测**：隐藏 → 点悬浮球，窗口 **1.4 秒**回来（`visible=True fg=True hung=False`），
日志写明 `open-dsh -> focused 已从后台打开（用 DSH 托盘图标的路径）`。

> **走过的两条死路，记下来免得再走：**
>
> 1. **再启动一次 DSH** ✗ —— 理论上运行中的实例会收到 `second-instance` 并调用
>    `focusPrimaryWindow()`，也就是同一个函数。实测：单独重新拉起 DSH，窗口
>    **10.8 秒都没回来**（进程数证明第二实例确实起来又退出了，说明单实例锁生效、
>    事件也发了，但那个函数没有把窗口弄回来）。所以这条路是死的，已经从代码里删掉。
> 2. **`dsh://open` 协议** ✗ —— 协议确实注册了（`HKCU\Software\Classes\dsh` → exe `"%1"`），
>    但 Electron 的 `open-url` 事件是 macOS 专有；Windows 上 URL 只作为 argv 传进去，
>    而 DSH 的 `second-instance` 处理器不看 argv。所以它和上面那条其实是同一条路。
>
> **还有一条留着的保险**：`SW_HIDE` 之后 Chromium 会停止合成，`Wake()`
> （1 像素尺寸抖动 + `RedrawWindow`）负责把画面逼回来 —— 它治的是「画面不刷新」，
> 和这里治的「页面 JS 被节流」是两回事，两个都要有。

|---|---|

| `GET /quit` | 退出 |

同时 `pet.log` 会在几何或状态变化时打印 `poll` 行（含光标窗口内坐标、球体方块、

> 它已经因为布局变动失效过两次（球在窗口里的位置、`side` 的来源）。能直接读日志里应用
> 自己吐出的字段，就不要自己再推一遍。

## 常见问题

- **双击启动器没反应 / 一闪就没**
  看 `%APPDATA%\DSH 悬浮球\pet-console.log`。启动器自己会在标准模式失败后自动改用兼容模式。
- **球在，但鼠标移上去不展开**
  展开由主进程轮询光标决定。设 `PET_DEBUG=1` 启动后看 `pet.log` 里的 `poll` 行
  （`overBall` / `overCapsule`）。
- **余额一直是 `--`**
  鼠标停在数字上会显示原因：通常是「没登录 DSH 账号，也没配 `DEEPSEEK_API_KEY`」，
  或登录态已失效。去 DSH「设置 → 账号与余额」登录一次即可。
- **余额和官网对不上**
  显示的是**平台钱包余额快照**；赠金单独列在悬浮提示里，不并入余额。
- **运行时间不对**
  取的是 DSH 进程启动时刻。DSH 被守护脚本反复拉起时时间会重置，这是预期行为。
- **点球没有把 DSH 拉到前面**
  看 `pet.log` 里 `open-dsh ->` 一行：
  `focused` = 成功；`focus-failed` = DSH 在运行但窗口没能前置，括号里会写明原因
  （`no-window` 一个窗口都不剩 / `blocked` 窗口不肯上前 / `error` 脚本本身出错）；
  `launched` = DSH 本来没在运行（或一个窗口都不剩），已把它启动起来。
  出现 `focus-failed` 时，灵动岛会用运行时间那一行短暂提示「DSH 未响应前置」，
  同时请把 `%APPDATA%\DSH 悬浮球\pet-console.log` 与 `focus-agent.log` 一起发出来 ——
  这两个文件会按顺序记录每一层失败的原因。
- **拖动大小滑块手感不对 / 球的大小没跟上滑块**
  拖动只更新目标值，实际直径由主进程逐帧缓动追上去，所以松手后会有一两百毫秒的收敛过程，
  这是刻意的。如果完全不跟手，看 `pet.log` 里 `poll` 行的 `size=` 是否在变。
- **设置面板自己关掉了**
  离开面板与悬浮球 220 ms 后自动收起，面板和灵动岛一起。重新悬停球体再点齿轮即可。
- **球被拖到看不见的地方**
  托盘图标右键 →「显示 / 置顶悬浮球」。

## 已知限制

- Windows 专属：窗口唤起、进程起始时间、托盘都依赖 Win32 / PowerShell。
- 未打包成单文件 exe。需要的话可接 electron-builder：`npx electron-builder --win portable`。
- 余额只覆盖 DeepSeek 官方账户口径；其它厂商余额需要各自对接。
- 窗口按最大球径建成 `860×908`（透明、点击穿透），比球本身大得多；这是「改尺寸时窗口一律不动」的代价。
  高度取决于设置面板有多高 —— 面板多一行开关，窗口就跟着高一点。它是全透明的，不参与命中测试。
- 灵动岛**换边**时窗口会横移 `|68 − size|`（最大 28 DIP）。这是「球的外侧边与面板永远齐平」
  的必然结果：那个齐平要求球的窗口内位置随朝向而定。那一帧已经用「主进程等回话再挪窗口 +
  渲染进程补一帧」补掉，但不是原子的，极端情况下仍可能残留一帧的错位。
